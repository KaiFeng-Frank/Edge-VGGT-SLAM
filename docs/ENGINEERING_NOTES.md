# 原 VGGT 工程问题记录

当前公开树只保留原 VGGT 模型的执行与验证记录。以下条目沿用原编号，未列出的旧条目留在 git 历史；本页没有其他模型或新增传统位姿前端的实现入口。各结果绑定当时固定的源码、输入、权重和运行范围。目标至少 20 Hz 新观测位姿、完整时延 P95 至多 100 ms，尚未达到。

## 6. 执行边界必须保留数组所有权和几何含义

- **触发：** 原模型返回 NumPy 视图，Solver/Submap 又长期保留像素和置信数组；硬件 adapter 若先释放输出，后续消费者可能读到失效或被覆盖的内存。
- **源码证据：** 执行合同固定 FP32 RGB、原帧顺序、相机 codec、depth/confidence 与世界到相机矩阵。模型局部相机矩阵与 SL4 项目性图坐标是不同对象。
- **方案：** 输入使用稳定存储；需长期保存的结果在 SDK release 前复制。对照捕获拥有自己的数组，比较前后哈希，错误明确向上传递。新公开 Solver 仅支持 `max_loops=0`；附加模型检索已移除，回环尚无替代实现。
- **验证边界：** 接口合同与小型检查不证明完整 NPU 模型或轨迹质量。图矩阵不可改名为已验证的全局 metric SE3。
- **链接：** [执行架构](../ARCHITECTURE.md)、[模型执行代码](../vggt_slam/model_execution.py)。

## 7. 代码许可、原权重与编译产物分别绑定来源

- **触发：** 仓库 BSD-2-Clause 容易被误用为原 VGGT 权重及其编译产物的授权依据。
- **证据：** 固定原 checkpoint 的模型卡声明 CC-BY-NC-4.0；固定 VGGT_SPARK 源码和发布补丁也保留其独立许可。它们不是仓库代码许可的同一个对象。
- **方案：** 保留实际 revision、SHA、文件大小、原代码归属和独立条款。不分发 checkpoint、捕获数组、含权重导出或 SDK 二进制。
- **验证边界：** 编译、精度转换或 BSD wrapper 不授予额外商业权利。本文只绑定实际使用的原 checkpoint，不推荐另一权重。
- **链接：** [原权重与代码许可](../MODEL_LICENSES.md)、[来源清单](../UPSTREAMS.json)、[第三方声明](../THIRD_PARTY_NOTICES.md)。

## 90. 迁移执行器必须保持原模型和完整验收分母

- **触发：** 组件执行成功或局部较快，可能被误报为完整 VGGT 新观测位姿吞吐。
- **证据：** 原 CPU FP32 两张 office 图像的 requested112、actual56×112 forward 为 3.831 s，尚未包含预处理、SL4 和发布。原权重 DINO 单块的 5.489 ms 是单块完整 I/O，不是完整模型时延；其 FP32 参考相对 L2 误差为 1.2253%。
- **方案：** 只改原算子、布局、内存、经验证不变的复用和 CPU/NPU 分工。逐项记录组件、完整 forward、输入到位姿/地图、启动、丢帧、结束工作与释放；同一个重叠图像不重复计入 fresh 分母。
- **验证边界：** 原模型实时、精度、地图周期、队列、8 GB 和 30 分钟运行均未完成验收。短固定输入测试不能代替连续真实观测。
- **链接：** [原模型测量](../MEASUREMENTS.json)、[项目约束](../AGENTS.md)。

## 92. 缓存独立 DINO 尾帧，不能缓存新上下文的 frame/global 输出

- **触发：** 连续 submap 共享图像，但它在新 pair 中的相机 token 角色和跨帧 global-attention 上下文会改变。
- **源码与保存证据：** 原 camera+depth 路径含 1,157,941,492 个参数以及各 24 个 DINO、frame 和 global block。仅保留第 4/11/17/23 层输出减少存储，未减少 Transformer 计算。历史三个原 CPU FP32 重叠 pair 的缓存测试把六个输入帧的 DINO 计算减少到四帧，pose/depth/confidence 与原参考逐字节相同；缓存 1,769,472 B。
- **方案：** 仅复用相同归一化像素、shape、dtype、固定模型/后端身份的独立 DINO patch tokens。每个新 pair 仍运行原 special tokens、frame/global、四轮 CameraHead 和 DPT。原 per-Linear 权重上传和中间往返须按完整调用检查。
- **验证边界：** 该短测不是任意 batch 或完整轨迹等价证明。历史热状态不同，时长比不构成因果加速。原 NPU 数值拒绝仍保留。
- **链接：** [原缓存证据](../results/patch_cache_v19.json)、[完整原 block 的数值拒绝](../results/hybrid_block_v20.json)、[原网络计算与存储预算](../results/capacity_v20.json)。

## 93. 缓存 A/B 对照须隔离图状态、预处理和姿态序列化

- **触发：** 两个方法共用 Solver 会依次追加不同 submap；从旧尺寸取参考、按文件名判命中或只比较节点数量也会使对照失真。
- **源码证据：** 原 loader 默认 518 宽、14 像素网格，crop/padding 可能改变共享图像的实际像素。无回环的连续 submap 尺度估计只用范数比的中位数，没有随机单应性采样。三个两图 pair 应各有 2/4/6 个节点和因子、1/2/3 个 submap；六节点只对应四个不同源图像。
- **方案：** 同一原模型、两个独立 Solver/map/graph，分别运行原 loader，交错 A/B、B/A、A/B。A 使用真正原 forward 并保持 B 的尾帧 token、key、所有权和计数。按同 pair、同输入保存五项原输出，FP32 与图 float64 门槛分别报告，literal bit equality 另列。图投影还须区分 inv(H)、K@inv(H) 和原 decomposition 的 camera-to-world pose；重叠时戳保留最新节点，最终源帧映射为 0/2/4/5。
- **验证边界：** 此处记录源审查与生成数组检查，不声明连续实验已经完成或达到实时目标。三组选择的重叠 pair 不是完整原始帧覆盖，也不是 GT 轨迹质量验收。实际模型与图优化仅可由板端执行。
- **链接：** [原 Solver](../vggt_slam/solver.py)、[原图结构](../vggt_slam/graph.py)、[submap 相机导出](../vggt_slam/submap.py)、[原 loader 与来源](../UPSTREAMS.json)。

## 94. 唯一模型约束必须落实到代码、参数和部署目录

- **触发：** 只将历史分支标记为停用，仍会留下可运行的加载入口和容易误用的配置。
- **修改：** 当前公开树移除附加模型及新增传统位姿前端的代码、测试、结果入口；Solver、主入口和 mapping worker 只支持原 VGGT 与 `max_loops=0`。不支持的配置在预处理、模型加载或图状态修改前拒绝。保留原 SL4 正常路径，板端活动第三方模型源码和权重目录分别只保留原 VGGT 与 `model.pt`。旧文件可追溯备份，不改写历史。
- **验证：** 103 项运行合同检查、31 项原 MLP 捕获合同检查、34 项原模型回归助手检查通过。部署后，在板端以原真实 TUM 输入完成 4 次原模型 forward；常规输出与历史原参考逐字节一致，两个独立首子图的 SL4 结果一致。此回归使用 112 尺度，不冒充 518 尺度或实时验收。
- **边界：** 回环检索和语义功能尚无符合唯一模型约束的新实现，不能宣称移除了依赖后仍具备这些功能。原 VGGT 自身的 similarity 数值测试不等于自然回环验证。
- **证据：** [唯一模型部署与板端回归](../results/original_only_v47.json)。

## 95. 原始 518 尺度的缓存一致性通过，速度目标仍未达到

- **实验：** 原 checkpoint、原 loader、CPU FP32、实际 `[2,3,392,518]`；4 张固定真实源图组成 3 个重叠子图，A/B、B/A、A/B 交错，两个独立 Solver。未使用旧尺寸的预测作为参考。
- **结果：** 五项完整预测与图快照均逐字节一致；DINO 只计算 4 帧，复用 2 次，尾帧缓存 4,243,456 B。所有原参数、源码和输入在实验前后保持一致，缓存关闭和进程亲和性恢复通过。
- **耗时与边界：** 6 次完整 forward 为 134.323、174.839、163.521、193.947、195.029、164.035 秒，尚未实时。调用后温度采样最高约 85.9°C，热状态未受控，最后一调用附近还有源码归档传输，不能据两次时长比宣称因果加速。峰值进程 RSS 为 6,755.1 MiB，测于 16 GB 板，不证明 8 GB 长期运行。
- **版本边界：** 518 对照使用清理前固定源码且仅执行原 VGGT；清理后的公开源码另经上条真实回归验证。4 张选择图像不是完整轨迹、实时到达队列或精度验收。
- **证据：** [完整数组哈希、逐项比较与计时范围](../results/original_only_v47.json)。

## 96. 两个完整块合并后，必须验证真实串接输出和实际 NPU 放置

- **问题：** 单独测试 frame0 和 global0 时，后者使用 CPU frame0 的保存输出，无法证明连续 NPU 执行的误差；把两个独立历史时长相加也不能证明合并收益。
- **实现：** 只为原 frame0/global0 加命名空间和一个原序 reshape，保留 86 个父节点、62 个父 initializer、36 个原参数张量及全部原算子。新的输出直接对照同一次原 CPU 捕获的最终 global0 输出。SDK 按输入/输出名称分别检查不同 rank3 shape，输出在 release 前复制。
- **实际验证：** 板端 CPU ORT 四次通过固定 `rtol=1e-4, atol=1e-5`；非量化 RKNN 编译完成。普通 NPU 四次输出稳定，但相对 L2 误差为 0.483569%、最大绝对误差 0.0304642，524,908 个元素超出该严格门槛，候选未采用。余弦相似度接近 1 不能代替轨迹精度验收。
- **耗时：** 独立普通调用的后三次完整 SDK IO 平均 338.683 ms；独立 profile 的 52 个内部算子全部在 NPU，两个 CPU 算子是输入/输出边界。profile 中 attention 总均值 119.107 ms，两个 MLP 总均值 98.621 ms。此处的 profile 时钟不能与普通 API 时钟混加。
- **边界：** 这是两个块的固定真实输入，不是完整 VGGT、新观测位姿速率或 30 分钟测试。原 DINO、其余 23 个 frame/global 对、CameraHead、DPT 和 SL4 尚在测量范围外。
- **复现与证据：** [配对执行源码](../deploy/rk3588/validation/original_pair/README.md)、[数值、放置与时钟收据](../results/original_pair_v48.json)。

## 97. 合并收益须用同进程真实链路对照，并剥离诊断计时的含义

- **实验：** 三个 SDK contexts 同进程常驻，以相同原 frame0 输入执行 `AB / BA / AB / BA`，共 12 次同步 SDK 调用。分开路径必须使用本次 NPU frame0 的自有输出，经同指针原序 view 直接交给 global0；保存 SHA 和实际指针证明没有 CPU 参考重置。
- **结果：** 四组分开/合并最终输出逐字节一致，两路径仍保持原 FP32 门槛拒绝。后三次 SDK 完整 IO 之和均值从 396.442 ms 降为 334.831 ms，本次短测下降 15.54%。
- **计时陷阱：** 带检查的完整路径均值为 426.910 / 334.951 ms；分开路径额外包含桥接有限性与前后 hash，不能把这部分诊断开销也算成融合固有收益。SDK IO 范围独立记录，包含输入、同步 run/get、自有复制和 release。
- **资源与边界：** 三 contexts 加诊断数组的进程峰值 RSS 324.008 MiB；四组短测的频率和温度仅采样、未控制。所有输出释放、context 销毁、源码输入复核与进程 affinity/environment 恢复通过。该结果支持继续使用配对执行形式做原模型研究，不证明整网精度或实时达标。
- **复现：** [同进程对照源码与实测说明](../deploy/rk3588/validation/original_pair_ab/RESULT.md)、[完整数值和计时范围](../results/original_pair_v48.json)。

## 98. 原模型预算必须使用新观测分母，缓存和地图降频不能消除主干计算

- **来源：** 9 个原 VGGT 文件的 SHA/AST、原捕获的矩阵尺寸及完整调用次数交叉验证；仅用标准库核算，没有主机模型执行。每个乘加记 2 FLOP，列出被排除的归一化、softmax、布局、传输和几何开销。12 项公式/保存元数据检查通过。
- **预算：** 实际 `[2,3,252,336]` 下，完整原 forward 的常规矩阵/卷积预算约 1.926 TFLOP；复用一个旧帧 DINO 后约 1.643 TFLOP，仅节省 14.70%。每个 overlap pair 只有一个新观测，20 Hz 对应平均有效预算约 32.864 TFLOP/s。较小的 `[2,3,84,112]` 对应约 3.728 TFLOP/s，但尺寸变化的轨迹质量仍未验收。
- **调度边界：** 假设原 backbone/Camera 保持新观测频率，而 dense head 每 2–5 秒执行一次，336 尺度仍约需 29.139–29.196 TFLOP/s。该调度尚未实现或验证 SL4/地图对齐，不能算作已交付功能。双向 global attention 的历史上下文不能按独立 DINO 的规则复用。
- **解释边界：** 上述是数学工作量，没有使用硬件峰值，也不是硬件不可实现的证明。FP16 唯一参数 payload、条件权重读取量、SDK DMA 与全板峰值内存必须分别报告；这些数值不证明 8 GB 或长期运行。
- **复现与完整算式：** [原模型预算和标准库检查](../deploy/rk3588/validation/original_budget/README.md)。

## 99. 原模型量化须隔离工具链，并保留独立的真实评测输入

- **问题：** RKNN 2.3.2 的 ARM64 依赖要求与生产 Torch 2.3.1 不同；把编译依赖装进生产环境，会改变原参考的执行条件。使用同一张捕获输入校准和评测，也无法检验量化对新输入的影响。
- **处理：** 从已核验的纯依赖 wheel 在板端新建独立环境，固定 Torch 2.2.0、NumPy 1.26.4、ONNX 1.16.1、ORT 1.16.0 和 RKNN 2.3.2；安装、依赖检查与 9 个模块的实际导入通过。原模型捕获仍使用生产 Torch 2.3.1，全程没有主机推理或校准。
- **真实数据：** 推理前固定 TUM fr1_xyz 的 8 组校准与 2 组评测，20 张 PNG 的索引、时间戳和 SHA 互斥，并排除旧评测图像。全部运行原 24 层 DINO；评测额外运行原 frame0/global0，保持同次原 FP32 参考。截停仅限定实验的数据捕获范围，不是删层加速。
- **验证：** 10 组板端捕获完成，24 份新数组、36 份原参数绑定、原 special-token 角色、RoPE 位置、完整调用计数及清理均通过独立保存数据审查。校准 dataset 只接收 8 份完整原输入，不接收位置编码或评测数组。
- **计时与内存边界：** 捕获含权重哈希、加载和检查共 142.998 s，峰值 RSS 1725.695 MiB；只触及前缀，不能证明完整模型 8 GB 运行。相同形状的校准前缀从 7.268 s 增至 15.944 s，A76 调用后温度采样较高；缺少同期频率和调度证据，不能据此认定热降频原因，也不能据短测给出持续吞吐。
- **复现：** [隔离工具链](../deploy/rk3588/validation/original_precision/toolchain/README.md)、[原模型数据捕获](../deploy/rk3588/validation/original_precision/capture/README.md)。

## 100. w8a8 配置不能代替真实算子放置、数值和速度检查

- **实测：** 原完整 frame0/global0 图经板端 8 组真实输入校准，四项 SDK 编译操作完成；产物 29,931,726 B，相比同图非量化版本小 45.86%。两份独立保留输入各执行四轮 AB/BA，总计 16 次普通 SDK 调用；各实现六次复测完整 IO 均值由 337.086 ms 降到 255.640 ms，局部下降 24.16%。
- **精度拒绝：** 原 Torch FP32 参考下，非量化两输入相对 L2 为 0.4453% / 0.4978%，PTQ 为 10.3122% / 10.5465%。两者都失败于固定 `rtol=1e-4, atol=1e-5`，不采用量化候选。新保留输入的 CPU ORT 复核也保留第一组 1/894,976 元素超限、第二组通过的结果；不因平均误差小而放宽门槛。
- **真实放置：** 独立新进程 profile 共 16 次调用。非量化 52 个内部算子均在 NPU；PTQ 为 51 个 NPU 算子及 1 个内部 CPU `Reshape:frame0/value_tp_rs`，另外都有 CPU 输入/输出边界。编译警告中的四个 transpose 提示不能计为最终四个 CPU 算子；最终编译表和运行时表必须分别核对。
- **瓶颈变化：** profile 八次均值中，frame/global MLP 分别从 50.089 / 48.877 ms 降到 16.053 / 16.090 ms，但 attention 从 40.988 / 78.020 ms 增至 45.215 / 87.572 ms。CPU reshape 均值 2.293 ms。最终表的 INT8 标签不证明 attention 内部算术全部为 INT8；编译常量仍包含 FLOAT16 norm 权重和 FLOAT norm bias。profile 算子时钟不能与普通 SDK IO 混加。
- **接口与因果边界：** SDK 的 INT8 输入描述符使用 zero-point 57、scale 0.0410780087，输出 zero-point 5、scale 0.0222544167；API 仍提交原 FP32 并取 FP32 自有输出，转换由 SDK 执行。两份输入仅 7 / 1 个元素落在输入描述符范围之外，这既没有模拟实际 SDK 舍入，也不能把约 10% 输出误差归因于截断。边界量化与内部近似影响尚未隔离。
- **工程结论：** 下一步优先研究原图的精度分配与 attention 布局，完整保留原算子和原权重；不能直接采用全局 w8a8，也不能据局部加速声称原模型实时。普通运行进程峰值 RSS 250.504 MiB 只包含两个首配对 contexts 与诊断数组，不证明完整模型的 8 GB 运行。
- **复现与审查：** [实际结果与收据 SHA](../results/original_precision_v49.json)、[数据、工具链和复现顺序](../deploy/rk3588/validation/original_precision/README.md)。生产执行路径未替换，回环仍无符合唯一模型约束的实现。

## 101. ADB 目录推送与 shell 返回码不能代替实验状态

- **触发：** 向已存在的板端目录再次 `adb push` 整个源码目录，会嵌套一个 basename。新增 heldout ORT launcher 因此未处于预期顶层，首次启动失败；该次没有执行 ORT，也没有输出实验目录。
- **处理：** 按明确目标逐文件推送六份新增源码，保留原冻结文件和失败日志；修正后的实验另从实际 `check.json` 读取结果。
- **检查边界：** 本机 ADB shell 调用可能在远端命令失败时仍报告退出码 0。源码存在、SHA 匹配、实际调用次数和最终 JSON 状态都须核对。后续 `numerical_rejected` 是真实数值失败，不能与前一次 launcher 未执行混为一谈。


## 102. FP16 可表示精度与原 FP32 组件门槛是不同问题

- **证据：** 仅读取两份已保存的原 FP32 输出，逐元素选择最近有限 FP16 值，并用全部 63,487 个不同有限值独立核对。即使每个元素都选取最优表示，两组仍分别有 272,497 / 272,573 个元素不能通过固定 `rtol=1e-4, atol=1e-5`；最近表示的相对 L2 下界约为 0.02072%。16 项生成数值检查通过。
- **INT8 边界：** v49 两份实际 PTQ 输出的所有元素都落在实测 FP32-scale INT8 输出格点。该格点相对原输出的最小相对 L2 为 4.219% / 4.269%，低于实际 10.312% / 10.546%。原输入每组 864 个 patch token 都在原 channel 555 有一个绝对值大于 4 的元素；这是保存数组分布，不是内部误差归因或新的校准规则。
- **处理：** 保留全部严格组件拒绝，不改门槛。区分表示本身的下界、实际计算误差和完整轨迹误差。原模型混合精度仍可作为诊断，但最终需独立测量 ATE/RPE、失败率与地图质量；组件相对 L2 不能转换为轨迹误差百分比。
- **边界：** 证明只涉及这些保存的参考张量和指定输出表示，不证明硬件不可能达到性能目标，也不证明任何轨迹验收通过。
- **复现：** [数值证明与纯 NumPy 检查](../deploy/rk3588/validation/original_mixed_precision/accuracy/RESOLUTION_NOTE.md)。

## 103. SDK 接受 Flash Attention 开关不证明目标芯片获得加速

## 104. MLP profile 分组包含融合算子，不能等同于原始 MLP 单独耗时

- **静态对应：** 原图中每个 MLP 有九个节点，四个 MLP MatMul 共占该 pair 常规 MatMul 预算的 60.24%；此比例不是耗时比例。原 norm2、LayerScale 和 residual 位于 MLP 外。
- **实际编译：** v49 的 fc2 编译算子折叠了 LayerScale，并以 ConvAdd 消费 residual。第 96/100 条的 MLP profile 分组应解释为融合后的 MLP/LayerScale/residual 算子组，不能用于声称九个原始 MLP 节点独立节省了相应时间。
- **处理：** 混合精度配置须针对 SDK 实际 tensor catalog，并核对原图到编译算子的对应、接口 dtype 和真实放置。保持原图与原权重来源，保留 SDK 生成的校准参数；只改变明确记录的精度分配。 [原图来源与融合范围收据](../deploy/rk3588/validation/original_mixed_precision/layout/public-original-layout-audit-r1.json)。


## 105. SDK 校准 catalog 不等同于可编辑的混合精度 selector 集合

- **实际失败：** 从板端 step1 生成的配置读取 95 个 catalog keys，保留全部校准参数，只为四个 FC1/GELU 输出请求 INT8、其余请求 FP16。实际 step2 在 `input` 处报 `Invalid operands name`，未执行 export，也未产生 NPU 候选。
- **完整性：** 失败调用后 SDK release、原始文件 SHA、cwd/environment 恢复均通过，失败收据保留。此前的生成配置检查证明文本/参数编辑范围正确，不证明 SDK 会接受每个 selector。
- **处理：** 通过静态解析 SDK 自己生成的中间图核对实际内部 operand；外部 API input/output 的表示必须由最终 SDK query 验证，不能把 calibration catalog 成员身份直接当成可编辑性证据。实际中间图含 62 个节点、56 个 initializer；95 个 catalog keys 可分为 65 个内部节点输出、24 个 initializer、2 个外部 I/O 和 4 个未出现在图中的 SDPA 估计项。重试限定四个明确 FC1/GELU 输出为 INT8、其余 61 个实际内部输出为 FP16，排除项的原量化参数保持不变。该修订版在板端编译成功，生成 48,050,420 B 产物，step2 API 用时 12.836 s；实际接口精度、算子放置和运行误差另行检查。

## 106. 跨 Python 版本复核计时均值须保持累加语义

- **触发：** 主机 CPython 3.13 的 `sum()` 与板端 CPython 3.11 的顺序浮点累加，在六次 SDK IO 均值上出现约 5.55e-17 s 差异；直接逐值核对收据曾因此拒绝。
- **处理：** 保存数据审查使用明确的逐项 `+=`，复现板端的相同调用顺序与六次分母。各阶段覆盖关系仍在整数纳秒上核对，profile 的整数微秒另算；没有放宽原 FP32 输出的数值门槛。


## 107. FC1/GELU 混合精度有局部耗时收益，但仍未通过原参考检查

- **实际运行：** 修订后的原图产物在板端完成 16 次普通 SDK 调用与另一个新进程的 16 次 profile 调用。每份输入各四轮 AB/BA，普通六次复测均值为 336.673 ms（浮点）和 319.928 ms（混合），本次局部下降 4.974%。完整 SDK IO 包含输入提交、run/get、自有复制与释放。
- **精度：** SDK 查询的混合候选逻辑输入/输出确为浮点；但两份原 Torch FP32 参考下，相对 L2 仍为 6.672% / 7.908%，对应浮点候选为 0.445% / 0.498%。保留全部严格组件失败，候选未采用；边界浮点不足以保证内部量化误差很小。
- **边界：** 四处输出的精度请求不代表全部 MLP 都以 INT8 运算。该短测只覆盖原 frame0/global0，两个输入均已用于开发，不能当作全新盲测、完整模型位姿精度、实时吞吐或长期稳定性结果。ATE/RPE 与地图质量仍需完整原模型链路测量。
- **证据：** [编译失败、修订与板端对照](../results/original_mixed_precision_v50.json)。
- **实际放置：** 最终表含 58 个算子，其中 56 个内部算子全部位于 NPU。两个 FC1/GELU 融合算子为 INT8，FC1 权重为 INT8、bias 标签为 INT32；FC2 权重为 FLOAT16、bias 为 FLOAT，FC2 的 GELU 与 residual 输入保持 FLOAT16。新增四处转换的独立 profile 均值合计 9.407 ms。算子标签不证明内部累加算术精度。
- **日志边界：** SDK stdout 的一条 INT64 reshape 常量记录被成功状态 JSON 打断。审查仅在内存移去精确 SHA 绑定的 168 B 插入，恢复该行；原始日志保持不变，全部编译行与 16 份运行表逐项核对。
- **复现：** [实际算子收据](../deploy/rk3588/validation/original_mixed_precision/layout/public-hybrid-operators-audit-r1.json)、[便携解析器与冻结清单](../deploy/rk3588/validation/original_mixed_precision/layout/hybrid-operators-publication-r1.json)。

## 108. 相同模型结构不能证明是指定的原始权重

## 109. 用新观测和发布完成时间测完整链路

新增原时间戳回放入口直接执行原 VGGT、原位姿解码、稠密子图和 SL4；每个已提交尾帧与最新新帧组成下一对，缓存只复用原 DINO 尾帧计算。798 帧 TUM fr1_xyz 回放得到 7 次新位姿/地图更新，0.195 Hz，包含解码、单槽排队、完整模型、SL4、文件原子发布和 EOF 排空的 P95 为 8.160 s；786 帧被覆盖、4 帧在解码前跳过。单槽队列避免积压，但不能让慢模型达到实时。缓存命中 6 帧，14 次输入图像出现仅计算 8 帧原 DINO，其余主干和头仍完整运行。地图含 98784 个局部点；仅短测，未验收轨迹质量或 8 GB 稳定运行。[可运行入口](../scripts/replay_original_vggt.py)、[实测](../results/original_timestamp_replay_v52.json)。

## 110. 完整模型接入 NPU 后，仍须测量整个执行链路

48 个原聚合器块全部在板端导出、编译并接入原 Aggregator 循环，保留原帧内/跨帧注意力、拼接、中间层和 target tokens；相机头复用原共享单步图，仍执行全部四次 refinement、原初始位姿、FP32 累加和原激活。17 个相同真实帧、每分支 16 次完整调用中，CPU、NPU 聚合器、NPU 聚合器加相机头平均服务耗时分别为 7.458 / 5.366 / 3.609 s。最后一条链路的相机头均值为 0.211 s，但聚合器含 DINO 仍需 2.633 s，深度头为 0.728 s；局部头部加速不等于整网实时。

三条轨迹使用完全相同的 17 个时间戳和 GT 关联。Sim3 对齐 ATE 为 0.17719 / 0.17857 / 0.17808 m；最后一条相对 CPU 的 ATE、平移 RPE、旋转 RPE 分别变化 +0.50% / +0.03% / +0.13%。RPE 使用相邻匹配帧的实际间隔，并非固定一秒。所有 FP16 严格张量门槛仍失败；这个短段、低分辨率、稀疏轨迹不足以接受整体质量。

完整时间戳回放得到四线程 0.312 Hz、P95 4.878 s，两线程 0.267 Hz、P95 6.239 s。瞬时频率采样曾显示两个大核簇分别为 408 / 2352 MHz，但实际两线程未改善吞吐，不能把单次频率观察直接当成瓶颈归因。仅改变进程线程和亲和性，没有更改系统频率策略。49 个常驻 RKNN contexts 的分项 DMA 查询合计约 3.59 GB；与进程 RSS 可能存在重复计数，应分别报告，不能相加后宣称 8 GB 可用或不可用。原始数组、导出权重和 SDK 产物均保留私有，公开源码、指标和来源哈希。[完整结果](../results/original_full_npu_v53.json)、[复现入口](../deploy/rk3588/validation/original_full_aggregator/README.md)。

## 111. DPT 原地 ReLU 会改变残差支路的实际输入

原 ResidualConvUnit 的第一次 ReLU 原地修改输入，所以后续残差相加使用的是 `ReLU(x)`。静态导出若按未修改的 `x` 建 skip，形状和权重都能正确却会改变结果。本次保留该别名语义、全部 62 个原参数张量、五组原位置常量与五次 `align_corners=True` 插值。板端原 FP32 logits 与 ORT 两帧比较均通过固定 `rtol=1e-4, atol=1e-5`，最大绝对误差分别为 4.47e-6 / 5.30e-6。原 DPT 的逐帧 chunk 循环、指数激活和最终拼接保留在 CPU；每对图像调用两次 SDK。[源码和对照](../deploy/rk3588/validation/original_depth/)、[结果](../results/original_dino_depth_v54.json)。

## 112. 扩大原模型的 NPU 执行范围后，瓶颈仍在聚合器

原 DINO 全 24 层采用单帧静态图，冷启动两帧沿独立 batch 轴逐帧执行；缓存命中时只计算一张新图，原 token 准备和最终归一化不变。同一组 16 对真实输入，接入 DINO 后完整服务均值为 3.087 s，再接入 DPT 为 2.665 s。后者的聚合器含 DINO / 相机头 / 深度头分别为 2.172 / 0.213 / 0.185 s。保存数据确认两个候选的 48 个位姿、内外参数数组逐字节一致；深度输出变化通过原 SL4 传播，ATE 为 0.174760 m（原 CPU 为 0.177191 m）。两候选对原 CPU 的 80 个严格张量比较仍全部失败，短段轨迹也不足以验收总体质量。

完整原时间戳回放实测 0.398 Hz、输入到发布 P95 3.212 s，12 个新位姿更新和 12 个稠密子图，785 帧未使用。74 个上下文均释放；峰值进程 RSS 为 7412.98 MiB，SDK DMA 单独记录。地图发布的 11 个间隔平均 2.468 s，但这只是 30.12 s 短测，未证明 30 分钟、8 GB 或闭环运行。SDK 编译日志含 `Unkown op target` 而 API 返回成功；整网实际执行完成，不据此宣称每个算子都在 NPU。不同版本是顺序运行，性能变化不作受控散热实验解释。[完整测量和边界](../results/original_dino_depth_v54.json)。

## 113. 合并相邻原模块时，必须保留帧内输出供原聚合器拼接

原 Aggregator 同时使用 frame 和 global 输出。只保留 global 的融合图无法直接替换完整链路。本次将全部 48 个原块组成 24 个双输出图：frame 调用一次 SDK，先复制两份输出再释放；global 验证收到同一帧输出的未改写连续 view，随后消费对应结果。层、参数、RoPE、拼接和中间层选择均保留。16 对相同真实输入的 80 个数组以及轨迹文件，与上一版 FP16 候选逐字节相同；原 FP32 的严格检查仍全部失败。

原 frame0/global0 的单核/三核交错短测显示单核更慢；三核普通完整 IO 均值分别为 24.014 / 20.851 ms，其中每块输入提交约 3.44 / 3.47 ms。另起 profile 上下文观察到 frame 布局转换合计 4.708 ms。普通计时不混入 profile 调用，也不把这两个块的放置推断为全部 48 层。合并后同 16 对图像的聚合器 SDK IO 从约 1.257 s 降至 1.121 s，完整服务仅从 2.665 s 降至 2.590 s；CPU 边界和其他模块仍占时间。

## 114. 模型主体移到 NPU 后，应重新测量 CPU 线程数

保持三核 NPU、原输出和 CPU 允许集合不变，将 Torch 线程从四改为一，完整服务均值从 2.590 s 降至 2.177 s；同一组 80 个输出数组和 `poses.tum` 逐字节一致。该观察来自顺序运行，不是交错散热实验，也不证明每个输入都数值相同。缓存 guard 的重复 eval 遍历和 dtype/device 字符串构造同时已简化，但前后两次状态检查仍保留；guard 均值仍约 0.180 s，没有据此宣称消除了该开销。

完整时间戳回放为 0.478 Hz、输入到发布 P95 2.669 s，14 次新位姿和稠密子图更新，783 帧未使用；13 个地图更新间隔均值 2.043 s，峰值进程 RSS 7296.82 MiB。所有 50 个 RKNN 上下文已释放。29.26 s 的短测不能证明 30 分钟、8 GB、闭环或整体地图质量；位姿实时目标仍未达到。[原始测量的公开摘要](../results/original_fused_aggregator_v55.json)、[复现](../deploy/rk3588/validation/original_fused_aggregator/README.md)。

## 115. 布局优化须同时核对 SDK 查询和实际输出

原 frame0 的 tokenwise 展平保持输出逐字节一致，却让普通 SDK IO 均值从 25.371 增到 26.102 ms，未采用。原 DINO block0 的通道布局图查询为 NHWC 输入、NCHW 输出；传 packed NCHW 数据且显式 API fmt0 时出现大误差，原因尚未确定。改用匹配查询的 NHWC 数据和 fmt1 后，最大绝对误差仍为 0.015625，相对 L2 为 0.00042133，未接入完整链路。不能把编译成功、形状相同或局部提速当作正确性证据。

## 116. 校准完整原聚合器后，速度和置信度必须分别验证

八对真实图像分别捕获全部 24 层输入，各层使用自己的八份原 FP32 激活，24 个未改写原 ONNX 图在板端完成 W8A8 PTQ 编译，耗时 531.677 s。独立的 17 张评价图像与校准图像索引不重叠，但仍来自同一短序列。16 对完整原模型加 SL4 的一线程服务均值从 2.1773 降至 1.8801 s；原 CPU 对照的 ATE / 平移 RPE 增加 2.38% / 3.66%，深度置信度平均相对 L2 误差为 39.46%，80 个严格 FP32 检查仍全部失败。完整时间戳回放为 0.570 Hz、P95 2.494 s。该回放包含校准图像，只作为吞吐证据；候选质量未验收。

## 117. SDK 浮点转换可移到 NEON，但收益应计入完整链路

## 118. 原 DINO 的显式 FP16 I/O 与缓存检查开销

## 120. INT4 整数计算正确仍可能有不可接受的量化误差

原 VGGT 内部 DINO block0 的 FC1（M=53、K=1024、N=4096）以 RKNN MatMul type10 进行独立 INT4 诊断。normal B 的 R2 子进程以 SIGABRT（-6）退出，最后刷盘记录是 B 的 rknn_matmul_set_io_mem 调用前；没有完成收据，清理无法核验，只定位到调用位置，SDK 内部根因仍未确立。R3 改用官方 native B 排列后成功，四次整数输出均与保留完整精度的 INT32 参考一致，此输入未发生 INT16 溢出，资源释放正常。R3 每个调用都刷盘，其计时不用于性能比较；单个输入无溢出也不能保证其它输入安全。

同一真实捕获上，裸跑的 per-tensor R4 与输入按行、权重按输出通道的 R5 均得到正确整数结果，但相对原 FP32 的 L2 误差分别为 29.32% 和 11.22%。R5 最大绝对误差为 9.042，217088 个输出中 216944 个（99.934%）未通过 rtol=1e-4、atol=1e-5；CPU 量化参考产生相同误差，输入量化后仅 3.89% 的整数元素非零。排除首次调用后，R4/R5 的平均 SDK run 为 16.376/16.239 ms，含输出同步和自有复制为 16.620/16.373 ms，均不含动态量化、反量化、初始化、参考计算和文件写入；量化加打包各约 152.7/152.9 ms，包含一次性权重准备。两次清理均正常。当前精度明显不合格且没有有价值的速度收益，停止这一 W4A4 INT4 分支；该组件结果未验证整网、轨迹或实时性能。

## 122. 性能记录必须包含实际 NPU 频率，不能只记录允许上限

## 128. 通用 MatMul 枚举不等于当前芯片支持，存储压缩也不等于混合精度算术

SDK 2.3.2 通用头文件有 FP16 激活与 INT8/INT4 权重的 type5–8 枚举，但同版本 User Guide §3.5.4.1 表 3-6 的 RK3588 列未列这些组合；Toolkit API 的 w8a16/w4a16 模式也限定在其它芯片。不能仅改枚举就声称本板可用，也不能把此前 type10、激活与权重都量化的 W4A4 结果当作 W4A16 实验。[官方支持表](https://github.com/airockchip/rknn-toolkit2/blob/v2.3.2/doc/02_Rockchip_RKNPU_User_Guide_RKNN_SDK_V2.3.2_EN.pdf)。

`do_quantization=False` 时的 `quantize_weight` 是另一个选项：文档只承诺部分权重压缩、缩小模型文件，没有承诺特定权重位宽、上述混合精度算术或推理提速。因此若继续测试，应分别核验实际文件/分配大小、完整调用耗时和原模型输出，不能从文件缩小推导实时性能。[官方 config 定义，第 7–9 页](https://github.com/airockchip/rknn-toolkit2/blob/v2.3.2/doc/03_Rockchip_RKNPU_API_Reference_RKNN_Toolkit2_V2.3.2_EN.pdf)。本轮仅核查固定版本文档与既有记录，没有执行不受支持的类型调用；不是对硬件所有可能实现的不可行性证明。

## 129. 权重压缩选项仍会触发目标平台的配置检查

固定 v64 原 pair0+pair1 四输出合图、ORT 检查和普通 FP16 编译来源后，只将 `quantize_weight=False` 改为 `True`；计划的 build 仍为 `do_quantization=False, dataset=None, auto_hybrid=False`。板端 SDK 2.3.2 在 `RKNN.config` 阶段即抛出 `ValueError`，消息为 `The quantized_dtype = 'w8a16' not support in 'rk3588'!`。实际调用记录只有失败的 config，尚未执行 load_onnx、build 或 export_rknn，未生成压缩 RKNN，也没有新的文件大小、SDK 内存、推理速度或输出精度结果。不能把原 v64 的结果归到这次失败尝试。

SDK release 正常返回，cleanup 为空；工作目录、TMPDIR 和 CPU 亲和性恢复，源码与原图的前后哈希一致。此次限制来自已安装版本的配置验证，不能推广为全部 SDK 版本或 native MatMul 硬件实现的不可行性证明。保留冻结构建脚本与失败证据后停止这一配置分支，不改 dtype 绕过检查，也不发布未执行的运行探针。[失败实测与证据哈希](../results/original_weight_compression_v65.json)、[复现命令与限制](../deploy/rk3588/validation/original_pair_group/README.md)。

## 131. 追踪构造器参数，避免漏掉原模型的目标特征

只看 `Aggregator(target_layer=20)` 默认值会误判目标出口。实际外层 `VGGT(target_layer=21)` 显式覆盖它，而 global 计数先递增再判断，因此原返回值来自零基编号 **global20**。即使 `compute_similarity=False`，原模型仍执行该张量的 clone 和 `norm + 1e-8` 归一化。整网分组必须额外返回原始 global20，并继续连接原 frame21；不能因为关闭闭环就删掉该返回值。

早期静态草稿把未来目标出口写成 global19；核对实际外层源码后，在整网图生成或执行前修正为 global20，并私有保留旧草稿。已执行的 pair0–4 组件不涉及该层，结果不受影响。完整分组的出口数是 2、2、2、3；同时保留四次原 Torch 拼接、24 项中间结果列表和目标特征归一化。整网对照额外保存这些中间返回值，在计时服务结束后落盘，避免只检查最终位姿而遗漏接口变化。

## 132. 板端编译也需要温度记录和独立失败目录

## 133. 整网收益和按时间戳回放分开验收

## 134. 数学相同的 MLP 图，也可能失去原来的 GELU 融合

同一原 frame0 MLP 的二维图保留所有权重和 106 个 token，但相对于冻结的原图，既展平了三维布局，也交换了第一个 GELU Mul 的输入顺序。SDK 将 Erf 和一次 Transpose 放到 CPU；单核 300 MHz 的独立编译图暖调用为 43.093 ms，native 为 31.725 ms。这不能证明优于现部署图。保留原失败对照后，同时恢复原 `[2,53,1024]` 形状及 `Mul(fc1, 1+erf(...))` 顺序，编译日志出现 NPU ConvExGelu/Conv，暖调用降到 15.139 ms，而 native 为 33.878 ms，结论反转。两次同时改动，不能将融合差异单独归因于某一项；这里的 NPU 归属来自编译日志，不是独立逐算子运行轨迹。

## 135. 原权重常驻 MatMul 上下文也要计算完整 CPU/NPU 边界成本

以原完整前向捕获的 frame0 输入及 18 份参数复原原 Block，复原输出逐字节一致，再 hook 出真实 MLP 输入。两层原权重按 FP16 native B `[N/16,K/32,16,32]` 一次打包上传，各保留独立上下文；不补齐或删除 token。A 为普通 FP16，C 为 FP32，偏置、GELU 和 eval dropout 保持原 CPU 路径。两个上下文共六个持久缓冲全部释放，最后一轮 native 16 次 run 与 compiled 4 次 run、4 次输出释放均对账成功。

最终交错比较排除各路线首个调用后，各仅有三次计时。native 慢 123.77%，其中原 CPU GELU 平均 19.363 ms；FC1/FC2 的裸 SDK run 约 2.472/8.898 ms。只报 MatMul run 会漏掉主要成本。native 在 compiled 比较前已预热，不能据此比较双方冷启动。该实现不接入整网；本轮没有新的轨迹、实时或长期稳定性验收，所有监控读数均为 300 MHz，最高采样 58.230°C。[原模型诊断、失效对照及源码](../deploy/rk3588/validation/original_native_mlp/README.md)。

## 136. 提前获得 CameraHead 输出不等于原 SL4 连续位姿已可用

112 输入、复用旧帧原 DINO 后，现有密集计算口径为每个新观测 93.201 GMAC，20 Hz 对应 1.864 TMAC/s（每 MAC 计两个 FLOP）。这不含归一化、GELU、数据转换及 SL4 等开销。官方宣传的 6 TOPS 没有在已核资料中给出对应的 FP16 峰值和计数定义，因此不能据此证明该目标可行或物理不可能。

新增默认关闭的 `--camera-split4` 完整对照及 `--rknn-camera-split4` 回放开关，只选择已经实测的原相机头四分块图。安装前仍验证原 checkpoint、69 个原头参数、四次原迭代、四处 FC1 重拼证明、编译和原 FP32 ONNX 检查收据；原 forward 源码逐字节不变。没有把旧图编译记录当作新图证明，也没有替换模型或同时保留两套头上下文。

## 141. 销毁失败时保留句柄，避免错误报告资源已释放

## 142. FC2 切 K 能改变执行效率，也会改变浮点归约顺序

## 151. 独占不可变执行会话减少重复遍历，保持原计算与保存输出

原 patch cache 在推理前后各完整遍历模型，retained 聚合器和 grouped DINO 又分别检查相同的参数树。固定生产 worker 在安装所有后端、观测 hooks 和 cache 后独占模型，期间不允许改模块、注册表、hooks、类、配置、Tensor 对象或 `.data`。新 `--immutable-execution` 默认关闭，只覆盖 cache fingerprint、retained lifecycle、DINO lifecycle 三个实例方法；保留原缓存入口、线程与句柄所有权、1343 项 Tensor 的版本／dtype／device／地址／requires_grad、方法、后端身份、输入输出和 SDK 释放检查。会话开始与关闭时执行原完整验证；关闭异常仍继续释放后端，外线程或活跃调用中的 close 会拒绝而不会拆除会话。这是明确收窄的执行契约，不声称与任意可变模型的逐次检测等价，不能把会话结束检查当作任意运行时修改都能立刻被发现。

同一原模型、图与 16 对真实图像，1 GHz 顺序整网对照平均完整服务 1.390134→1.248281 s（减少 10.20%），后 15 次平均 1.356822→1.227044 s（减少 9.56%）。32 份 NPZ 的 160 项数组和保存轨迹逐字节相同；原 FP32 严格检查仍为 0/80。每路线 12 个 SDK context、262 次调用均正常结束，候选完成 32 次版本遍历和 64 次方法检查，首尾完整验证通过、3 个覆盖恢复。初始化和关闭验证在每对服务时间之外；两轮不是交错测量，不能将全部时间差都归于唯一因素。首次 harness 因 receipt 父目录预先创建了比较器要求不存在的输出目录而在模型加载前失败；r2 将 receipt 独立放置后完成，原失败保留。

生产入口显式启用该开关后，798 个原时间戳输入产生 26 次新观测位姿，包含 EOF 排空的 28.891830 s 内为 0.899908 Hz，完整 input-to-pose P95 1.366577 s；此前为 0.775988 Hz／1.570522 s。启动 38.752203 s、峰值进程 RSS 3920.418 MiB 单列。队列容量 1，797 个生成帧加 1 个解码前跳过帧覆盖全部 798 个时间戳，27 个交付包含 seed，770 个覆盖。选帧改变，固定对照输出一致性不能替代该回放轨迹的 ATE/RPE。仍未达到每秒一次及 20 Hz／100 ms 目标，未完成相机、30 分钟、物理 8 GB 或闭环验收。22 项新增小替身检查与原回放测试共 87 tests、7 subtests 通过；实际板端运行与这些生成测试分开记录。源码、只含指标的收据与复现见 [不可变执行会话](../deploy/rk3588/validation/original_immutable_execution/README.md)。

## 152. 原全局特征依赖图像对上下文，简单池化尚不能承担回环检索

## 153. 原参数可逆缩放通过 FP32 检查，仍不能保证 INT8 精度改善

针对原 frame0/global0 双层图，在板端用八个原校准输入捕获四处实际 Norm 输出：norm1→QKV、norm2→FC1。不能把块入口当作 FC1 激活。alpha=0.5 的通道尺度取最邻近二的整数幂，Norm gamma/beta 除以尺度，后继原权重的输入通道乘以尺度。仅 12 个图初始化量改变，所有原节点、其他参数与两个完整出口保留，原 checkpoint 文件不变。每个改写参数均可逐字节逆变换；此外两个真实输入的四个完整 FP32 输出也与原图逐字节相同，其中一个输入的图像与校准集无 SHA 交集。可逆参数证明和实际浮点输出检查不可互相代替。

相同八个输入、相同 RKNN 2.3.2 W8A8/channel/normal 配置编译一个候选；1 GHz、core mask 7，以 ABCCBA×6 在两个输入分别交错比较，每路线 22 个 warm 调用。统一 FP32 输入、want_float=1 两出口，完整 SDK 路线含转换、复制、释放、有限性检查。原 FP16／普通 INT8／缩放 INT8 平均为 32.682／20.957／20.666 ms。无校准图像交集的输入上，frame/global 相对原 FP32 ONNX 的 L2 误差从普通 INT8 的 9.545%／12.352% 仅降到 9.393%／12.220%，原 FP16 为 0.422%／0.473%；三路线均未过固定原 FP32 严格门槛。与普通 INT8 的 1.39% 计时差不构成新的稳定加速证据。候选未接入整机，也未扩编到 24 对。

单独的六次 profile 确认每图 54 行 NPU 算子，INT8 路线包含原八个线性算子的 INT8 标签。B/C 外部输入输出量化刻度完全相同；仅对保存数组做量化再反量化，输入约 4.13%、两个输出约 2.96%／3.40% L2 误差且无裁剪。这些不是完整推理误差的下界，也不证明 SDK 舍入约定，只说明内部 Norm 缩放没有改变这些外部量化刻度。普通与 profile 共 78 次 SDK 调用、156 个输出全部释放、六个 context 全部关闭；15 个控制器采样与 156 个调用前后采样均为 1 GHz，最高 53.615°C，均恢复 300 MHz/userspace 与原 min/max。当前整机仍是 v77 的 0.899908 Hz／P95 1.366577 s，未新增实时或质量验收。源码、真实收据和复现见[原参数缩放诊断](../deploy/rk3588/validation/original_power2_smoothing/README.md)。
